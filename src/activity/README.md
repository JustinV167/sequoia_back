# Activity tracking

Interactions of a student inside a course are stored in two layers.

## 1. Raw event log (`activity_events`)

Append-only. One row per interaction, including the client timestamp, the
server reception time, the course/module/lesson/exercise ids, the time spent,
media position, score and a free-form `metadata` JSONB column.

| Event | When it is sent | Useful fields |
| --- | --- | --- |
| `course_opened` | The course viewer mounts. | `metadata.totalLessons` |
| `course_closed` | The student leaves the viewer. | `durationMs` (wall time) |
| `module_viewed` | The student opens a module for the first time in the session. | `metadata.moduleTitle` |
| `lesson_viewed` | A lesson becomes the active one. | `metadata.lessonTitle`, `metadata.lessonType` |
| `lesson_time` | Every 15 s and when the tab is hidden. | `durationMs` (active time delta) |
| `lesson_completed` | The student advances past the lesson or finishes the course. | `progressPercent = 100` |
| `video_play` / `video_pause` / `video_seeked` / `video_progress` / `video_ended` | Native video events. | `positionSeconds`, `durationSeconds` |
| `exercise_started` | An exercise block mounts. | `metadata.exerciseType` |
| `exercise_answered` | The student clicks **Comprobar**. | `durationMs`, `score`, `attemptNumber`, `metadata.answer`, `metadata.status` |
| `exercise_retried` | The student clicks **Reintentar**. | — |

Every event carries an `eventId` generated by the browser. The API inserts with
`ON CONFLICT (event_id) DO NOTHING`, so a retried batch (common on
`visibilitychange`/`pagehide`) is applied only once.

Client timestamps are clamped: events older than 30 days or more than 60 s in
the future use the server reception time instead.

## 2. Rolling aggregates

Updated inside the same transaction as the raw insert, only for newly stored
events.

| Table | Grain | Columns of interest |
| --- | --- | --- |
| `course_activity` | user + course | `visits`, `total_time_seconds`, `lessons_completed`, `exercises_attempted`, `exercises_correct`, `progress_percent`, `last_lesson_id`, `completed_at` |
| `module_activity` | user + course + module | `visits`, `total_time_seconds`, `lessons_completed`, `progress_percent` |
| `lesson_activity` | user + course + lesson | `visits`, `total_time_seconds`, `completed_at`, `last_position_seconds`, `progress_percent` |
| `exercise_activity` | user + course + exercise | `starts`, `retries`, `attempts`, `correct_attempts`, `best_score`, `solved_at`, `last_answer` |

`progress_percent` is never taken from the client. It is recomputed as
`distinct completed lessons / lessons_total`, where `lessons_total` comes from
the course template in MongoDB. The same number is written to
`enrollments.progress_percent` (and `status = completed` at 100) so the student
dashboard reflects the real progress as soon as the viewer closes.

## API

All routes require an authenticated session.

| Method | Route | Access |
| --- | --- | --- |
| `POST` | `/api/activity/events` | Enrolled student (batch of 1–50 events) |
| `GET` | `/api/activity/courses/:courseId/me` | Enrolled student |
| `GET` | `/api/activity/courses/:courseId/summary` | Course owner (teacher) |
| `GET` | `/api/activity/courses/:courseId/students` | Course owner (teacher) |
| `GET` | `/api/activity/courses/:courseId/students/:studentId` | Course owner (teacher) |
| `GET` | `/api/activity/courses/:courseId/breakdown` | Course owner (teacher) |
| `GET` | `/api/activity/courses/:courseId/events` | Course owner (teacher) |

`/events` accepts `studentId`, `moduleId`, `lessonId`, `exerciseId`, `type`,
`limit` (max 200) and `offset`.

## Frontend

`src/lib/activity.ts` contains `CourseActivityTracker`: it buffers events,
deduplicates the events React can emit twice in `StrictMode`, flushes every
1.5 s, and drains the queue before closing the viewer so the dashboard can
reload fresh progress.

`src/lib/activityContext.tsx` exposes the current module/lesson scope to
`ExerciseBlock` without prop drilling. Teacher previews do not mount a tracker,
so the analytics only contain real student interactions.

The teacher dashboard exposes these aggregates in the **Estadísticas** section
(`#/teacher/statistics`): course selector, KPIs, performance by module, lesson
and exercise, plus the per-student table. The table can be searched by name or
email and every row opens a per-student report with daily activity, module
progress, lesson time and exercise accuracy charts. The screen consumes
`summary`, `students` and `breakdown` in a single request batch, and the
detail uses `students/:studentId`.

## Quizzes

Quiz lessons carry an optional `quiz` object in the course content:

```json
{ "timeLimitMinutes": 10, "maxAttempts": 1, "passScore": 60 }
```

The simple editor exposes these three fields per quiz lesson.

Before starting, the student sees the warning card: number of questions, time
limit, score over 100, pass score, attempts left and previous best score. The
server creates the attempt only when the student presses **Comenzar**, so the
timer starts at that exact moment.

`quiz_attempts` keeps the authoritative deadline, the latest autosaved answers,
the final score and the soft anti-cheat counters. The client autosaves 1.2 s
after each change and on `visibilitychange`/`pagehide`, so a power outage loses
at most the last second of work. On return, the student resumes the same
attempt with the remaining server time.

Anti-cheat measures (non-blocking):

- Server-side deadline and server-side grading.
- Answers can only be saved while the attempt is active and before expiry.
- One active attempt at a time and a configurable attempt limit.
- Deterministic shuffling of questions and multiple-choice options per attempt.
- Tab changes, hidden time and paste events are counted and saved.
- Late submissions are graded with the answers already stored on the server.

While an attempt is in progress the viewer locks navigation: the previous/next
buttons and the exit button are hidden, lesson links and the mobile section
selector are disabled, and Escape cannot close the course. The lock is released
when the quiz is submitted or its time expires.

Routes:

| Method | Route | Access |
| --- | --- | --- |
| `GET` | `/api/quiz/courses/:courseId/lessons/:lessonId` | Enrolled student |
| `GET` | `/api/quiz/courses/:courseId/lessons/:lessonId/stats` | Course owner (teacher) |
| `POST` | `/api/quiz/courses/:courseId/lessons/:lessonId/start` | Enrolled student |
| `GET` | `/api/quiz/attempts/:attemptId` | Attempt owner |
| `PUT` | `/api/quiz/attempts/:attemptId` | Attempt owner (autosave) |
| `POST` | `/api/quiz/attempts/:attemptId/submit` | Attempt owner |

Quiz results feed the teacher statistics: course KPIs (attempts, passed, average
score), the quizzes panel in the course breakdown and the quiz panel of every
student detail chart. Clicking a quiz opens the quiz detail: configuration,
summary, daily deliveries, accuracy per question, monitoring events and a table
of results by student (`lessons/:lessonId/stats`).

## Extending

To add a new interaction:

1. Add the value to `ActivityEventType` on both the API and the client.
2. Send it from the component with `tracker.track({ type, moduleId, lessonId, ... })`.
3. If it should affect an aggregate, handle it in `ActivityService.applyAggregates`.

The raw table can be pruned periodically (for example, keep 12 months) without
losing the rolling aggregates.
